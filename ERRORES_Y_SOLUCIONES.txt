============================================================
 ERRORES ENCONTRADOS Y SOLUCIONES — Control Gastos App
============================================================

────────────────────────────────────────────────────────────
1. ICONO DE ANDROID NO SE ACTUALIZA (muestra el default)
────────────────────────────────────────────────────────────

PROBLEMA:
  Al reemplazar los PNGs en mipmap-*, la app seguía mostrando
  el icono verde de Android por defecto.

CAUSA:
  La carpeta mipmap-anydpi-v26/ contiene XMLs de "adaptive icon"
  que en Android API 26+ tienen PRIORIDAD sobre los PNGs.
  Si esos XMLs apuntan a recursos incorrectos o a sí mismos
  (referencia circular), Android no puede resolver el icono
  y muestra el default.

  En nuestro caso, ic_launcher.xml tenía:
    <foreground android:drawable="@mipmap/ic_launcher" />
  Esto es una REFERENCIA CIRCULAR: ic_launcher → XML → ic_launcher → XML...

SOLUCIÓN:
  1. Generar archivos ic_launcher_foreground.png separados en cada
     carpeta mipmap-* (icono centrado en fondo transparente, tamaño 108dp).
  2. Los XMLs adaptativos deben apuntar a ic_launcher_foreground:
       <foreground android:drawable="@mipmap/ic_launcher_foreground" />
  3. El background se define como color en colors.xml:
       <color name="ic_launcher_background">#e0f2fe</color>

ARCHIVOS AFECTADOS:
  - generate-icons.mjs (genera los foreground PNGs)
  - android/.../mipmap-anydpi-v26/ic_launcher.xml
  - android/.../mipmap-anydpi-v26/ic_launcher_round.xml
  - android/.../values/colors.xml

LECCIÓN:
  NUNCA borrar mipmap-anydpi-v26/ sin recrearla correctamente.
  NUNCA apuntar foreground a @mipmap/ic_launcher (referencia circular).
  Siempre usar un recurso _foreground separado.


────────────────────────────────────────────────────────────
2. FAVICON DE VITE (timer) APARECE EN VEZ DEL ICONO CUSTOM
────────────────────────────────────────────────────────────

PROBLEMA:
  Tras borrar los iconos del proyecto, la web mostraba un icono
  de timer/reloj (el favicon por defecto de Vite).

CAUSA:
  El index.html referenciaba archivos de icono que ya no existían:
    <link rel="icon" href="/icon.svg" />
  Al no encontrarlos, el navegador usaba el favicon cacheado de Vite.

SOLUCIÓN:
  1. Siempre regenerar los iconos ANTES de borrar los antiguos
     (o inmediatamente después).
  2. Añadir cache-buster a las URLs: href="/icon.svg?v=2"
  3. Para forzar en el navegador: Ctrl+Shift+R (hard reload).

LECCIÓN:
  Usar ?v=N en las URLs de favicon para invalidar caché del navegador
  cada vez que se cambie el icono.


────────────────────────────────────────────────────────────
3. CACHÉ DE ANDROID: ICONO NO CAMBIA TRAS REBUILD
────────────────────────────────────────────────────────────

PROBLEMA:
  Incluso después de regenerar los PNGs y hacer cap sync,
  el icono en Android seguía siendo el antiguo.

CAUSA:
  Android cachea los iconos del launcher agresivamente.
  El build cache (android/app/build/) conserva recursos antiguos.

SOLUCIÓN:
  1. Borrar android/app/build/
  2. Ejecutar: npx cap sync android
  3. DESINSTALAR la app del dispositivo/emulador
  4. Reinstalar desde Android Studio

LECCIÓN:
  Para cambios de icono en Android, SIEMPRE:
  - Limpiar build cache
  - Desinstalar la app del dispositivo antes de reinstalar


────────────────────────────────────────────────────────────
4. ESTRUCTURA DE ICONOS ANDROID — REFERENCIA RÁPIDA
────────────────────────────────────────────────────────────

Archivos necesarios por carpeta mipmap-*:
  - ic_launcher.png          (icono legacy, cuadrado)
  - ic_launcher_round.png    (icono legacy, redondo)
  - ic_launcher_foreground.png (foreground para adaptive icon, fondo transparente)

En mipmap-anydpi-v26/:
  - ic_launcher.xml          (adaptive icon: background + foreground)
  - ic_launcher_round.xml    (adaptive icon: background + foreground)

Tamaños de foreground (108dp por densidad):
  mdpi:    108x108
  hdpi:    162x162
  xhdpi:   216x216
  xxhdpi:  324x324
  xxxhdpi: 432x432

El icono real dentro del foreground debe ocupar ~60% del canvas
(zona segura interior) para que no se recorte.

5. DIST/ CONTIENE ARCHIVOS ANTIGUOS
────────────────────────────────────────────────────────────

PROBLEMA:
  Tras borrar iconos de public/, quedaban copias antiguas en dist/.

CAUSA:
  dist/ es el output de "npm run build" y no se limpia automáticamente
  al borrar archivos de public/.

SOLUCIÓN:
  Borrar dist/ manualmente o hacer npm run build de nuevo.

LECCIÓN:
  Al hacer cambios en public/, recordar que dist/ puede tener
  copias antiguas. Hacer build limpio o borrar dist/.

6. GRADLEW NO EXISTE EN EL PROYECTO
────────────────────────────────────────────────────────────

PROBLEMA:
  Al intentar ./gradlew clean, el comando no se encontró.

CAUSA:
  Capacitor no siempre genera el wrapper de Gradle.
  El proyecto se compila desde Android Studio que usa su propio Gradle.

SOLUCIÓN:
  En vez de gradlew clean, borrar manualmente android/app/build/:
    Remove-Item -Recurse -Force "android\app\build"

LECCIÓN:
  No asumir que gradlew existe. Usar borrado manual del build
  o compilar desde Android Studio.

7. PANTALLA EN BLANCO TRAS BORRAR FOTOS O "BACK TO FOLDERS"
────────────────────────────────────────────────────────────

PROBLEMA:
  Al confirmar "Delete Photos" o pulsar "Go Back to Folder" en la
  CompletionScreen, la app mostraba una pantalla en blanco permanente.
  Había que recargar o cerrar/abrir la app.

CAUSA:
  AnimatePresence mode="wait" bloquea el montaje de la nueva página
  hasta que la animación de salida termine. Si cualquier re-render
  (actualización del store, cierre del diálogo Radix) interrumpe esa
  animación, la nueva página NUNCA se monta → pantalla en blanco.

SOLUCIÓN:
  1. Eliminado mode="wait" de AnimatePresence en App.jsx.
  2. Cambiado a crossfade con grid overlap (ambas páginas visibles
     durante la transición).
  3. Añadido pointerEvents: "none" en exit y initial para que la
     página que sale no bloquee clicks en la nueva.

ARCHIVOS AFECTADOS:
  - src/App.jsx

LECCIÓN:
  AnimatePresence mode="wait" es frágil: cualquier re-render durante
  la exit animation puede romper la transición. Usar crossfade con
  pointer-events es más robusto.

8. FOTOS NO SE BORRAN DEL SISTEMA DE FICHEROS
────────────────────────────────────────────────────────────

PROBLEMA:
  Al dar "Delete Photos", las fotos se eliminaban del store en memoria
  pero seguían existiendo en el disco / sistema de ficheros.

CAUSA:
  removePhotos() solo eliminaba las fotos del array en memoria y
  revocaba blob URLs. No borraba los archivos reales.
  Además, <input webkitdirectory> (API antigua) da acceso de solo
  lectura — no permite borrar archivos del disco.

SOLUCIÓN:
  1. Usar File System Access API (showDirectoryPicker con mode:'readwrite')
     en vez de <input webkitdirectory>. Esto da permisos de escritura.
  2. Nuevo método loadFromDirectoryHandle() en photoStore.js que guarda
     el dirHandle del directorio padre en cada foto.
  3. deleteFile() en capacitorPhotos.js ahora usa dirHandle.removeEntry()
     para borrar el archivo real del disco (web) o Capacitor Filesystem
     (nativo Android).
  4. removePhotos() es ahora async y llama deleteFile() antes de
     eliminar del store.

ARCHIVOS AFECTADOS:
  - src/lib/capacitorPhotos.js (deleteFile con dirHandle)
  - src/lib/photoStore.js (loadFromDirectoryHandle, removePhotos async)
  - src/pages/Home.jsx (showDirectoryPicker)
  - src/components/EmptyState.jsx (showDirectoryPicker)

LECCIÓN:
  <input webkitdirectory> es solo lectura. Para borrar archivos del
  disco en web, SIEMPRE usar File System Access API con mode:'readwrite'.
  Solo funciona en Chrome y Edge.

9. AL ABRIR OTRA SUBCARPETA, CARGA CONTENIDO DE LA ANTERIOR
────────────────────────────────────────────────────────────

PROBLEMA:
  Tras abrir subcarpeta A, volver al menú y abrir subcarpeta B,
  se mostraban las fotos de A en vez de B.

CAUSA (doble):
  a) FrozenRoutes en App.jsx usaba key={location.pathname} que siempre
     es "/clean" para todas las subcarpetas. React reutilizaba la misma
     instancia con el useRef congelado apuntando a ?folder=A.
  b) CleanFolder.jsx usaba useRef para congelar folderName del primer
     montaje. Los useState (decisions, history) solo se inicializaban
     en el primer mount con datos de la carpeta A.

SOLUCIÓN:
  a) Cambiado key a pathname+search en AnimatedRoutes para que cada
     ?folder=X cree una instancia nueva.
  b) Eliminado useRef para folderName; se lee directo de searchParams.
  c) Añadido useEffect que resetea decisions, history, showConfirm,
     showGrid y startFromIndex cuando folderName cambia.

ARCHIVOS AFECTADOS:
  - src/App.jsx (key del AnimatePresence)
  - src/pages/CleanFolder.jsx (folderName sin ref + reset useEffect)

LECCIÓN:
  Si usas AnimatePresence con key para transiciones de página,
  incluir SIEMPRE los query params en el key cuando el contenido
  depende de ellos. No congelar con useRef valores que deben cambiar.

10. GRID MUESTRA FOTOS BORRADAS (IMÁGENES ROTAS)
────────────────────────────────────────────────────────────

PROBLEMA:
  Tras borrar fotos, el grid seguía mostrándolas como imágenes rotas
  (sin visualización porque ya no existían en disco).

CAUSA:
  usePhotoStore() devolvía siempre la misma referencia a photoStore.
  Los useMemo en CleanFolder dependían de `store`, pero como la
  referencia nunca cambiaba, allPhotos no se recalculaba tras
  removePhotos() → el grid usaba datos stale.

SOLUCIÓN:
  usePhotoStore() ahora devuelve Object.create(photoStore) — un
  wrapper con nueva identidad en cada tick del store. Así los useMemo
  que dependen de `store` se recalculan automáticamente.

ARCHIVOS AFECTADOS:
  - src/lib/usePhotoStore.js

LECCIÓN:
  Cuando un hook devuelve un objeto singleton como dependencia de
  useMemo, el memo NUNCA se invalida. Devolver un wrapper con nueva
  identidad (Object.create) o incluir un counter en las deps.
